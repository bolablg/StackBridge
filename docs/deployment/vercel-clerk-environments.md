# Vercel and Clerk environment boundary

This runbook defines how StackBridge chooses its Clerk instance at deploy time. It is intentionally explicit because a preview that accidentally uses the production identity environment can create confusing account state and weaken the separation between testing and the live application.

## Required mapping

| Surface | Vercel target | Clerk instance | Expected key prefixes | StackBridge mode |
| --- | --- | --- | --- | --- |
| Local contributor runtime | Local | None by default | No Clerk keys required | `local` |
| Development branch preview | Preview | Development | `pk_test_`, `sk_test_` | `hosted` |
| Pull-request or staging preview | Preview | Development | `pk_test_`, `sk_test_` | `hosted` |
| Production release | Production | Production | `pk_live_`, `sk_live_` | `hosted` |

The production release is the reviewed `staging` → `main` promotion. The public production origin is `https://stackbridge.bolablg.com`. Preview origins are generated by Vercel and should be configured in the development Clerk instance when they need to be used for sign-in testing.

## Vercel variables

In the `bolablg-projects/stackbridge` Vercel project, open **Settings → Environment Variables** and set the variables below for the specified target. Vercel stores the values; this document never contains the values themselves.

### Preview

Set these variables for **Preview** deployments:

- `STACKBRIDGE_MODE=hosted`
- `DATABASE_URL` for the intended preview database
- `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` from the Clerk development instance (`pk_test_…`)
- `CLERK_SECRET_KEY` from the same Clerk development instance (`sk_test_…`)
- `STACKBRIDGE_ADMIN_EMAIL`
- `CLERK_AUTHORIZED_PARTIES` containing only the approved preview origins
- Any optional `CLERK_JWT_KEY`, `CLERK_FRONTEND_API_URL`, or Resend variables needed by that preview

### Production

Set these variables for **Production** deployments:

- `STACKBRIDGE_MODE=hosted`
- `DATABASE_URL` for the production database
- `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` from the Clerk production instance (`pk_live_…`)
- `CLERK_SECRET_KEY` from the same Clerk production instance (`sk_live_…`)
- `STACKBRIDGE_ADMIN_EMAIL`
- `CLERK_AUTHORIZED_PARTIES` containing `https://stackbridge.bolablg.com` and only other explicitly approved production origins
- Any optional `CLERK_JWT_KEY`, `CLERK_FRONTEND_API_URL`, or Resend variables needed in production

The publishable key is designed to be available to the browser. The secret key, JWT key, database URL, and email-delivery key are server-side secrets. Do not copy them into an issue, pull request, README, screenshot, or shell transcript.

## Branch and deployment flow

1. Work on a `dev-*` branch. A push produces a Vercel Preview and uses the Preview variables above.
2. The quality workflow opens or reuses the draft pull request into `staging`. Pull-request and staging validation remain Preview deployments and use the development Clerk instance.
3. After review, merge `staging` into `main`. The production deployment uses only the Production variables and the production Clerk instance.
4. If a deployment was created before an environment-variable change, redeploy that exact commit. Environment changes are applied at build time; an existing deployment does not retroactively receive new variables.

Do not manually promote a preview to production with the wrong target variables. If Vercel project settings change, verify the production branch and environment assignments before the next release.

## Safe verification

Verify the configuration without printing secret values:

- In Vercel, confirm `STACKBRIDGE_MODE` is `hosted` for both Preview and Production.
- Confirm each target has both Clerk variables and that they are assigned only to the intended target.
- In the relevant Clerk instance, confirm the publishable-key prefix: `pk_test_` for Preview and `pk_live_` for Production.
- Test sign-in with a non-production account on a Preview URL, then test the production origin separately.
- Confirm an unapproved account reaches the StackBridge access gate and that approved/admin access works as expected.

Never paste a full key into a diagnostic command. Checking only the prefix and whether the variable is present is sufficient.

## Relationship to legal-auth

[`legal-auth`](../../legal-auth/) is a separate, public BOLABLG.com legal and account-support site. It has no Clerk SDK, no Clerk environment variables, and no authenticated routes. Its StackBridge product record links to `https://stackbridge.bolablg.com` only; it does not link to a preview URL and does not participate in the Preview/Production key split.

Keep `clerk.bolablg.com` reserved for Clerk's production custom domain, Frontend API, and OAuth callbacks. Keep `legal.bolablg.com` as the separate public Vercel hostname. Never point the Clerk hostname to Vercel.

## Rotation and incident response

If a key may have been exposed, rotate it in Clerk first, update only the affected Vercel target, and redeploy. Do not attempt to repair a leaked value by committing a replacement or placing it in this repository. Review both the Vercel deployment logs and the Clerk instance configuration after rotation.
